# Часть 1. Проект

## Пайплайн

```
download → prepare → augment → featurize → train → evaluate
```

| Стадия      | Что делает                                                                                         | Выход                       |
|-------------|----------------------------------------------------------------------------------------------------|-----------------------------|
| `download`  | скачивает датасет с Kaggle                                                                          | `data/raw`                  |
| `prepare`   | стратифицированно делит размеченные изображения на train/val/test (70/15/15)                        | `data/prepared`             |
| `augment`   | генерирует новый датасет: по 2 аугментированные копии каждого train-изображения                     | `data/augmented`            |
| `featurize` | извлекает признаки предобученной на ImageNet CNN (EfficientNet-B0, 1280 признаков)                  | `data/features`             |
| `train`     | обучает классификатор (`logreg`, `svm`, `random_forest`) на исходных или исходных + аугментированных данных | `models/model.joblib` |
| `evaluate`  | считает accuracy / F1 / precision / recall на val и test, строит матрицу ошибок                      | `metrics/eval.json`, `plots/` |

Тестовая выборка **никогда не аугментируется**, поэтому результаты с аугментацией и без неё сравнимы.

## Структура репозитория

| Путь | Назначение |
|---|---|
| `src/common.py` | пути к каталогам, чтение `params.yaml`, запись JSON |
| `src/download.py` … `src/evaluate.py` | по одному скрипту на стадию пайплайна |
| `dvc.yaml` | описание стадий: команда, зависимости, параметры, выходы |
| `dvc.lock` | зафиксированные хэши всех входов и выходов (генерируется DVC) |
| `params.yaml` | все параметры: разбиение, аугментация, признаки, модель |
| `run_experiments.sh` | серия из 6 экспериментов |
| `metrics/`, `plots/` | метрики и графики текущей версии модели (хранятся в git) |
| `data/`, `models/` | данные и модель под управлением DVC (в git только `.gitignore`) |
| `.dvc/config` | настройки DVC, в том числе адрес удалённого хранилища |

## Воспроизведение

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
# Kaggle API token: ~/.kaggle/access_token (или ~/.kaggle/kaggle.json)
dvc repro
```

## Эксперименты

```bash
# один эксперимент
dvc exp run -n svm-aug -S train.model=svm -S train.use_augmented=true

# история экспериментов и сравнение (-A — по всем коммитам, см. раздел «Демонстрация»)
dvc exp show -A --only-changed
dvc exp diff <exp1> <exp2>

# выбрать модель из истории: восстановить её параметры, модель и метрики в рабочую копию
dvc exp apply <exp>

# получить эксперименты из GitHub
dvc exp pull origin --all
```

## 1. Задача и общая идея решения

**Цель работы** — познакомиться с инструментами MLOps: версионированием экспериментов и автоматизацией
ML-пайплайнов.

**Что требовалось по заданию:**

1. Создать удалённый репозиторий.
2. Построить автоматический пайплайн (предобработка → обучение → оценка) и провести эксперименты минимум
   с тремя моделями, показав на защите перемещение по истории экспериментов.
3. Сделать аугментацию и сохранить новый датасет.
4. Повторить эксперименты на исходных + аугментированных данных.
5. Сравнить результаты с аугментацией и без.

**Задача машинного обучения** — многоклассовая классификация изображений: по фотографии определить один
из 75 видов бабочек.

**Идея решения в одном абзаце.** Обучать сверточную сеть на процессоре долго, поэтому взята готовая сеть
EfficientNet-B0, обученная на ImageNet. Её используют как «переводчик» картинки в вектор из 1280 чисел
(признаков). На этих векторах обучаются три классические модели: логистическая регрессия, SVM и случайный лес.
Все шаги оформлены в пайплайн DVC, каждый запуск с новыми параметрами сохраняется как эксперимент DVC, а
эксперименты отправлены на GitHub.

**Используемые инструменты:**

| Инструмент | Версия | Для чего |
|---|---|---|
| Git + GitHub | — | версионирование кода, удалённый репозиторий, хранение истории экспериментов |
| DVC | 3.67 | пайплайн, версионирование данных и моделей, эксперименты |
| PyTorch + torchvision | 2.14 / 0.29 | предобученная EfficientNet-B0, преобразования изображений |
| scikit-learn | 1.9 | классификаторы, стандартизация, метрики |
| Kaggle API | 2.2 | автоматическая загрузка датасета |
| pandas, Pillow, matplotlib | — | таблицы, изображения, графики |

## 2. MLOps

**MLOps** (Machine Learning Operations) — набор практик, переносящих идеи DevOps (автоматизация,
версионирование, CI/CD, мониторинг) на машинное обучение. Цель — чтобы модели можно было надёжно
воспроизводить, сравнивать, выпускать в эксплуатацию и обновлять.

**Чем ML сложнее обычной разработки.** Результат зависит не только от кода, но и от:

- **данных** (какая версия датасета, как разбита, как предобработана);
- **параметров** (гиперпараметры модели, параметры предобработки);
- **окружения** (версии библиотек, зерно генератора случайных чисел).

Если версионировать только код, через месяц невозможно ответить, на каких данных и с какими параметрами
получена модель с accuracy 0,91. MLOps решает именно эту проблему.

**Основные принципы MLOps:**

| Принцип | Как реализован в работе |
|---|---|
| Версионирование кода | Git, GitHub |
| Версионирование данных и моделей | DVC: хэши в git, сами файлы в кэше и удалённом хранилище DVC |
| Автоматизация пайплайна | `dvc.yaml` + `dvc repro`: все шаги одной командой |
| Отслеживание экспериментов | `dvc exp run / show / diff / apply` |
| Воспроизводимость | `dvc.lock`, фиксированные seed, `requirements.txt`, загрузка данных как стадия |
| Конфигурация вне кода | все параметры в `params.yaml` |

**Уровни зрелости MLOps** (классификация Google):

- **Уровень 0** — ручной процесс: ноутбуки, ручной запуск, модели передаются файлами.
- **Уровень 1** — автоматизированный ML-пайплайн: шаги описаны кодом и запускаются автоматически,
  данные и эксперименты версионируются, возможно автоматическое переобучение.
- **Уровень 2** — CI/CD для пайплайнов: изменения кода автоматически тестируются, пайплайн собирается и
  разворачивается, модель мониторится в эксплуатации.

Эта работа соответствует **уровню 1**: пайплайн автоматизирован и воспроизводим, эксперименты
версионируются, но нет CI/CD, развёртывания модели и мониторинга.

**Жизненный цикл ML-модели:** сбор данных → подготовка → обучение → оценка → развёртывание →
мониторинг (дрейф данных, падение качества) → переобучение. В работе покрыты этапы от сбора до оценки.

## 3. Git и GitHub

**Git** — распределённая система контроля версий. Основные понятия:

- **коммит** — снимок состояния всех файлов проекта; у каждого коммита есть уникальный хэш (SHA-1),
  автор, дата, сообщение и ссылка на родителя;
- **ветка** — подвижный указатель на коммит (`main`);
- **ссылка (ref)** — именованный указатель на коммит. Ветки — это ссылки `refs/heads/...`, теги —
  `refs/tags/...`. DVC хранит эксперименты в собственном пространстве ссылок `refs/exps/...`;
- **удалённый репозиторий (remote)** — копия репозитория на сервере (`origin` → GitHub);
- `git push` / `git pull` — отправка изменений на сервер и получение изменений с него.

**GitHub** — веб-сервис для хостинга git-репозиториев. Задание рекомендует GitLab, но разрешает другие
инструменты: для этой работы они эквивалентны, а DVC работает с любым git-хостингом.

**Почему данные нельзя хранить в git:**

- git хранит каждую версию каждого файла целиком и рассчитан на текстовые файлы с построчными
  изменениями;
- датасет в 166 МБ (6500 картинок) и его аугментированная версия раздули бы репозиторий, и каждый
  `git clone` скачивал бы все версии всех картинок;
- GitHub ограничивает размер файлов (100 МБ) и репозитория.

Поэтому в git лежат только маленькие **метаданные** (хэши) данных, а сами данные хранит DVC. Каталоги
`data/` и `models/` исключены из git через `.gitignore`, который DVC создаёт автоматически.

## 4. DVC

**DVC (Data Version Control)** — инструмент с открытым исходным кодом, который работает поверх git и
добавляет ему:

1. версионирование больших файлов (данных и моделей);
2. описание и запуск пайплайнов с кэшированием;
3. управление экспериментами;
4. работу с метриками и графиками.

### 4.1. Как DVC версионирует данные

- DVC считает **MD5-хэш** содержимого файла и кладёт файл в **кэш** `.dvc/cache/files/md5/<первые 2
  символа>/<остальные>`. Это адресация по содержимому (content-addressable storage): одинаковые файлы
  хранятся один раз.
- Для каталога считается хэш списка хэшей его файлов (запись вида `md5: dd21….dir` в `dvc.lock`).
- В git попадает только хэш: в `dvc.lock` для выходов стадий (или в `.dvc`-файле, если данные добавлены
  командой `dvc add`).
- В рабочей копии лежит копия файла из кэша или ссылка на него (reflink, hardlink, symlink, copy — зависит
  от файловой системы и настроек).
- Переключение версии: `git checkout <коммит>` меняет хэши в `dvc.lock`, а `dvc checkout` подставляет в
  рабочую копию файлы с этими хэшами из кэша.

**Удалённое хранилище (remote)** — место, где хранится копия кэша для обмена и резервирования: S3, Google
Drive, SSH, HTTP, Azure или локальный каталог. В этой работе используется локальный каталог
`~/dvc-storage/machine-learning-engineering` (см. `.dvc/config`).

- `dvc push` — отправить файлы из кэша в remote;
- `dvc pull` — скачать из remote файлы, на которые ссылается текущий `dvc.lock`, и разложить их в рабочую
  копию (= `dvc fetch` + `dvc checkout`).

Git хранит «что и какой версии», DVC remote хранит «сами байты».

### 4.2. Пайплайны: `dvc.yaml`

Пайплайн — набор **стадий** (stages) в `dvc.yaml`. Для каждой стадии указывают:

| Поле | Значение | Пример из работы |
|---|---|---|
| `cmd` | команда запуска | `python src/train.py` |
| `deps` | зависимости: код и входные данные | `src/train.py`, `data/features` |
| `params` | параметры из `params.yaml`, от которых зависит стадия | `train` (весь раздел) |
| `outs` | выходы, которые DVC положит в кэш | `models/model.joblib` |
| `metrics` | файлы метрик (JSON/YAML) | `metrics/eval.json` |
| `plots` | данные для графиков | `plots/confusion.csv` |

`cache: false` у метрик и графиков означает, что файл не кладётся в кэш DVC, а хранится прямо в git: он
маленький и его удобно видеть в истории.

**Граф зависимостей (DAG).** DVC строит граф, связывая выход одной стадии с зависимостью другой. Например,
`data/prepared` — выход `prepare` и вход `augment`, значит `augment` идёт после `prepare`. Граф
выводится командой `dvc dag`. Он ацикличный: циклические зависимости запрещены.

### 4.3. `dvc repro` и `dvc.lock`

`dvc repro` воспроизводит пайплайн:

1. для каждой стадии в порядке графа сравнивает текущие хэши `deps`, значения `params` и хэши `outs` с
   записанными в `dvc.lock`;
2. если всё совпадает, стадия пропускается («Stage didn't change, skipping»);
3. если что-то изменилось, стадия перезапускается, а за ней все зависящие от неё стадии;
4. после выполнения стадии новые хэши записываются в `dvc.lock`, выходы кладутся в кэш.

**Run-cache.** DVC запоминает результаты всех запусков (`.dvc/cache/runs`). Если стадия уже запускалась
с точно такими же зависимостями и параметрами, DVC не выполняет её заново, а восстанавливает выходы из
кэша. Именно поэтому при смене модели извлечение признаков (около 10 минут) не повторяется.

**`dvc.yaml` и `dvc.lock`:**

| | `dvc.yaml` | `dvc.lock` |
|---|---|---|
| Кто пишет | человек | DVC автоматически |
| Содержание | что делать: команды, зависимости, выходы | результат: конкретные хэши и значения параметров последнего запуска |
| Аналогия | `requirements.txt` | `poetry.lock` / `package-lock.json` |

`dvc status` показывает, какие стадии устарели относительно `dvc.lock`. Если всё актуально, выводится
«Data and pipelines are up to date».

**Пример.** Изменили `augment.rotation_deg` в `params.yaml`. Тогда перезапустятся `augment` (её параметр
изменился), `featurize` (изменился её вход `data/augmented`), `train` и `evaluate`. Стадии `download` и
`prepare` останутся нетронутыми.

### 4.4. Параметры: `params.yaml`

Все настраиваемые значения вынесены из кода в `params.yaml`, а скрипты читают их через
`common.load_params()`. Это даёт две вещи:

- DVC отслеживает конкретные ключи параметров и перезапускает только зависящие от них стадии;
- параметры можно переопределять при запуске эксперимента: `dvc exp run -S train.model=svm`.

### 4.5. Эксперименты DVC

**Эксперимент** — запуск пайплайна с изменёнными параметрами или кодом, который DVC сохраняет
автоматически, не засоряя историю git обычными коммитами и ветками.

**Как это устроено:**

- `dvc exp run` выполняет `dvc repro` в рабочей копии и создаёт **скрытый git-коммит** со всеми
  изменёнными файлами: `params.yaml`, `dvc.lock`, метрики, графики;
- коммит записывается в ссылку `refs/exps/<хэш базового коммита>/<имя эксперимента>`. Он не попадает в
  `git log` и `git branch`, но хранится в репозитории и отправляется на GitHub;
- данные и модели эксперимента лежат в кэше DVC, а в коммите эксперимента — их хэши в `dvc.lock`;
- **базовый коммит (baseline)** — коммит, от которого запущен эксперимент. В этой работе все 6
  экспериментов запущены от первого коммита `main`.

**Основные команды:**

| Команда | Что делает |
|---|---|
| `dvc exp run -n имя -S ключ=значение` | запустить эксперимент с изменёнными параметрами |
| `dvc exp run --queue ...` + `dvc exp run --run-all` | поставить эксперименты в очередь и выполнить (можно параллельно `-j N`) |
| `dvc exp show` | таблица экспериментов с параметрами и метриками (`-A` — по всем коммитам, `--only-changed` — только меняющиеся столбцы) |
| `dvc exp diff A B` | разница метрик и параметров между экспериментами |
| `dvc exp apply имя` | восстановить эксперимент в рабочую копию: параметры, `dvc.lock`, метрики и выходы из кэша (без коммита) |
| `dvc exp branch имя ветка` | сделать из эксперимента обычную git-ветку |
| `dvc exp remove имя` | удалить эксперимент |
| `dvc exp push origin --all` / `dvc exp pull origin --all` | отправить эксперименты в git-remote и DVC-remote / получить их |
| `dvc metrics show` / `dvc metrics diff` | метрики текущей версии / сравнение с другим коммитом |
| `dvc plots show` / `dvc plots diff` | построить HTML с графиками (например, матрицей ошибок) |

**Как выбиралась модель («перемещение по истории»):**

```bash
dvc exp show -A                   # смотрим таблицу
dvc exp apply logreg-aug          # восстанавливаем лучший по val эксперимент
git add -A && git commit -m "Выбрана модель logreg-aug"
dvc push && git push origin main
dvc exp push origin --all
```

### 4.6. DVC и альтернативы

| Инструмент | Что умеет | Отличие от DVC |
|---|---|---|

## 6. Данные: разбиение, стратификация, утечка

**Зачем три выборки:**

| Выборка | Роль | Аналогия |
|---|---|---|
| train (70 %) | на ней модель обучается (подбирает свои веса) | учебник |
| val (15 %) | на ней сравниваем модели и выбираем лучшую | пробный экзамен |
| test (15 %) | на ней один раз оцениваем выбранную модель | настоящий экзамен |

Если выбирать модель по test, test перестаёт быть независимым: мы «подгоняем» выбор под него, и оценка
становится оптимистичной. Поэтому модель выбиралась по **val**, а test использовался только для
итоговой оценки.

**Стратификация** — разбиение, при котором доля каждого класса во всех выборках одинакова. Классы
содержат от 71 до 131 изображения. При случайном разбиении без стратификации в val или test какой-то класс
мог бы почти не попасть.

**Утечка данных (data leakage)** — ситуация, когда при обучении модели доступна информация из
тестовых данных. Пример утечки, которую мы предотвратили: если бы аугментированные копии тестовых
изображений попали в train, модель видела бы при обучении «почти те же» картинки, что и при проверке, и
accuracy была бы завышена. Поэтому аугментация делается **после** разбиения и **только** для train.

**Дисбаланс классов.** Он умеренный: соотношение максимума к минимуму 131/71 ≈ 1,8. Поэтому кроме accuracy
смотрим F1-macro, который учитывает все классы с равным весом.

## 7. Сверточные сети и перенос обучения

### 7.1. Сверточная нейронная сеть (CNN)

- **Свёртка** — операция, при которой небольшой фильтр (например, 3×3) скользит по изображению и в каждой
  позиции считает взвешенную сумму пикселей. Фильтр реагирует на определённый локальный узор (край, угол,
  текстуру). Веса фильтров подбираются при обучении.
- **Иерархия признаков:** первые слои находят края и цветовые пятна, средние — текстуры и части
  объектов (узор крыла, усики), последние — целые объекты.
- **Пулинг** уменьшает пространственный размер карт признаков. **Глобальный усредняющий пулинг** (global
  average pooling) усредняет каждую карту в одно число и превращает тензор C×H×W в вектор длины C.
- В конце обычно стоит полносвязный слой-классификатор.

### 7.2. ImageNet

Датасет примерно из 1,28 млн изображений 1000 классов. Сеть, обученная на нём, умеет извлекать
универсальные визуальные признаки, полезные и для других задач. Среди классов ImageNet есть и несколько
видов бабочек.

### 7.3. Перенос обучения (transfer learning)

Знания модели, обученной на одной задаче, используются в другой. Два варианта:

| | Извлечение признаков (feature extraction) — **наш вариант** | Дообучение (fine-tuning) |
|---|---|---|
| Что обучается | только новая модель поверх признаков | новый классификатор + часть или все слои сети |
| Веса сети | заморожены | меняются |
| Скорость | быстро: признаки считаются один раз | медленно: каждая эпоха = прогон всех картинок вперёд и назад |
| Нужен GPU | нет | практически да |
| Качество | хорошее | обычно выше |

**Почему выбран feature extraction:** GPU нет. Дообучение на CPU заняло бы часы на каждый эксперимент, а
так признаки считаются один раз за 10 минут, и каждая модель обучается за секунды. Это позволило провести
серию экспериментов, что и было целью работы.

### 7.4. EfficientNet-B0

- Семейство сетей EfficientNet (Tan, Le, 2019). Главная идея — **составное масштабирование** (compound
  scaling): глубина, ширина и разрешение сети увеличиваются согласованно по общей формуле. B0 — базовая,
  самая маленькая модель семейства (B0…B7).
- Строится из блоков **MBConv** (инвертированный residual-блок из MobileNetV2 с depthwise-свёртками) с
  механизмом внимания Squeeze-and-Excitation.
- 5,3 млн параметров, точность top-1 на ImageNet — 77,7 %. Это лучше ResNet-50 (≈76 %) при впятеро
  меньшем числе параметров, поэтому сеть хорошо подходит для CPU.
- Выход после глобального пулинга — **вектор из 1280 признаков**.

**Предобработка** (`weights.transforms()`), обязательно та же, что при обучении на ImageNet:

1. изменение размера до 256 пикселей по меньшей стороне (бикубическая интерполяция);
2. вырезание центральной области 224×224;
3. перевод в тензор со значениями от 0 до 1;
4. нормализация по каналам: mean = (0,485; 0,456; 0,406), std = (0,229; 0,224; 0,225) — средние и
   стандартные отклонения ImageNet.

## 8. Модели классификации

Все модели обёрнуты в конвейер `make_pipeline(StandardScaler(), модель)`.

### 8.0. StandardScaler

Приводит каждый признак к среднему 0 и стандартному отклонению 1: `x' = (x − μ) / σ`. Параметры μ и σ
считаются **только на train** и затем применяются к val и test: так конвейер устроен автоматически, и
утечки нет. Логистическая регрессия (регуляризация, сходимость оптимизатора) и SVM с RBF-ядром (расстояния
между точками) чувствительны к масштабу признаков. Случайному лесу масштаб безразличен, но шаг оставлен
для единообразия.

### 8.1. Логистическая регрессия (LogisticRegression)

- Линейная модель: для каждого класса k считается оценка `z_k = w_k·x + b_k`, а функция **softmax**
  превращает оценки в вероятности `p_k = exp(z_k) / Σ exp(z_j)`. Предсказывается класс с максимальной
  вероятностью.
- Обучение — минимизация **кросс-энтропии** (логарифмической функции потерь) с **L2-регуляризацией**.
- Параметр **C = 1,0** — обратная сила регуляризации: чем меньше C, тем сильнее штраф за большие веса и
  тем проще модель.
- Решатель **lbfgs** — квазиньютоновский метод оптимизации. `max_iter = 3000` — предельное число итераций.
- Число весов: 75 классов × (1280 + 1) ≈ 96 тыс.

### 8.2. Метод опорных векторов (SVC)

- Ищет разделяющую поверхность с **максимальным зазором** (margin) между классами. Решение определяется
  только ближайшими к границе объектами — **опорными векторами**.
- **Ядро RBF** `K(x, x') = exp(−γ‖x − x'‖²)` позволяет строить нелинейные границы: неявно переводит данные
  в пространство более высокой размерности (kernel trick).
- **C = 10** — штраф за нарушение зазора: большой C требует точнее разделять обучающие данные (риск
  переобучения).
- **gamma = 'scale'** = 1 / (число признаков × дисперсия X). После стандартизации это ≈ 1/1280. Чем больше
  γ, тем более «локальное» и извилистое решение.
- Многоклассовость — схема **«один против одного»** (one-vs-one): обучается 75·74/2 = 2775 бинарных
  классификаторов, итог определяется голосованием.

### 8.3. Случайный лес (RandomForestClassifier)

- Ансамбль из **500 решающих деревьев**. Каждое дерево обучается на **бутстреп-выборке** (случайной
  выборке с возвращением; этот приём называется bagging). В каждом узле дерево выбирает лучший признак
  только из случайного подмножества размером √1280 ≈ 36.
- Итоговый ответ — **голосование** деревьев. Случайность делает деревья разными, а усреднение уменьшает
  дисперсию (переобучение) отдельных деревьев.
- `max_depth = None` — деревья растут до чистых листьев.

### 8.4. Почему логистическая регрессия оказалась лучшей

- Признаки предобученной сети уже «разложили» классы так, что их можно отделить почти линейно: последний
  слой самой EfficientNet тоже линейный. Значит, линейной модели на этих признаках достаточно.
- Данных мало относительно размерности: около 60 примеров на класс в 1280-мерном пространстве.
  Регуляризованная линейная модель в таких условиях обобщает лучше всего, а гибкие модели (SVM с RBF,
  глубокие деревья) легче переобучаются.
- Случайному лесу плохо подходят плотные непрерывные признаки высокой размерности, где информация
  распределена по многим признакам сразу: каждое разбиение в дереве смотрит на один признак.

## 9. Метрики качества

Для класса k: **TP** — объекты класса k, предсказанные как k; **FP** — объекты других классов,
предсказанные как k; **FN** — объекты класса k, предсказанные как другой класс.

| Метрика | Формула | Смысл |
|---|---|---|
| Accuracy | верных ответов / всех ответов | общая доля правильных ответов |
| Precision_k | TP / (TP + FP) | из предсказанных как k, сколько действительно k (точность) |
| Recall_k | TP / (TP + FN) | из всех настоящих k, сколько нашли (полнота) |
| F1_k | 2·P·R / (P + R) | гармоническое среднее точности и полноты |

**Усреднение по классам:**

- **macro** — простое среднее метрики по 75 классам: каждый класс весит одинаково, независимо от размера.
  Используется в работе;
- **weighted** — среднее, взвешенное по размеру классов;
- **micro** — считается по суммарным TP/FP/FN. В многоклассовой задаче micro-F1 = accuracy.

**Почему F1-macro.** При дисбалансе accuracy может оставаться высокой, даже если модель плохо распознаёт
малочисленные классы. F1-macro такие провалы покажет.

**Матрица ошибок (confusion matrix)** — таблица 75×75: строка — истинный класс, столбец — предсказанный.
В работе она нормирована по строкам, поэтому на диагонали стоит recall каждого класса. Яркая диагональ
означает хорошую модель, а внедиагональные пятна — пары видов, которые модель путает.

## 10. Аугментация данных

**Аугментация** — искусственное увеличение обучающей выборки за счёт преобразований, которые меняют
изображение, но не меняют его класс. Модель видит больше вариантов (ракурсы, освещение, масштаб), лучше
обобщает и меньше переобучается.

**Офлайн и онлайн аугментация:**

| | Офлайн — **наш вариант** | Онлайн |
|---|---|---|
| Когда | заранее, один раз | на лету при каждой эпохе обучения |
| Результат | новый датасет на диске | ничего не сохраняется |
| Плюсы | датасет версионируется (требование задания); признаки можно посчитать один раз | бесконечное разнообразие |
| Минусы | ограниченное число вариантов, место на диске | требует обучения сети по эпохам |

Задание требует «сохранить новый датасет», а с замороженной сетью признаки считаются один раз, поэтому
выбран офлайн-вариант.

**Использованные преобразования** (`params.yaml → augment`):

| Преобразование | Параметры | Что имитирует |
|---|---|---|
| RandomResizedCrop | 70–100 % площади → 224×224 | другой масштаб и кадрирование |
| RandomHorizontalFlip | p = 0,5 | зеркальный ракурс (бабочки симметричны) |
| RandomRotation | ±25° | наклон камеры или бабочки |
| ColorJitter | яркость, контраст, насыщенность ±30 %, оттенок ±0,05 | другое освещение, камеру, баланс белого |
| GaussianBlur | ядро 5, σ = 0,1…2,0, p = 0,2 | расфокус, смаз |

**Чего сознательно нет:** сильного изменения оттенка (у многих видов главный признак — цвет крыльев, и
сдвиг hue мог бы «превратить» один вид в другой) и вертикального отражения (на фотографиях бабочки почти
всегда в естественной ориентации).

**Объём:** 4549 исходных + 9098 аугментированных = 13 647 обучающих изображений (×3).

## 11. Разбор результатов

### 11.1. Влияние аугментации

| Модель | Δ Accuracy (val) | Δ Accuracy (test) | Δ F1-macro (test) |
|---|---:|---:|---:|
| LogisticRegression | +0,31 п.п. | −0,41 п.п. | −0,29 п.п. |
| SVM (RBF) | +3,08 п.п. | +1,95 п.п. | +1,24 п.п. |
| RandomForest | −0,31 п.п. | +0,51 п.п. | +0,50 п.п. |

- **SVM выиграл больше всех.** С C = 10 и RBF-ядром он склонен к переобучению при 60 примерах на класс.
  Аугментированные копии добавляют точки вокруг исходных в пространстве признаков, области классов
  становятся «плотнее» и шире, граница — устойчивее.
- **Случайный лес** — изменения в пределах шума, причём на val и test с разными знаками.
- **Логистическая регрессия** — тоже в пределах шума: +0,31 п.п. на val, −0,41 п.п. на test, то есть
  3–4 картинки из 975. Модель уже близка к пределу качества, который дают замороженные признаки.

### 11.2. Статистическая значимость

- В test 975 изображений: одно изображение = 1/975 ≈ **0,1 п.п.** accuracy.
- Стандартная ошибка оценки accuracy ≈ √(p(1−p)/n) = √(0,91·0,09/975) ≈ 0,0092, то есть
  95 %-й доверительный интервал ≈ **±1,8 п.п.**
- Значит, различия меньше 1–2 п.п. (у LR и RF) статистически незначимы. Прирост SVM (+1,95 п.п. на test и
  +3,08 п.п. на val, в одну сторону) — единственный заметный эффект.

### 11.3. Почему аугментация помогла мало

1. **Сеть заморожена.** Аугментация сильнее всего помогает, когда обучаются сами свёрточные слои: сеть
   учится быть инвариантной к преобразованиям. Наши признаки фиксированы.
2. **EfficientNet обучалась на ImageNet с похожими аугментациями** (кадрирование, отражения), поэтому её
   признаки уже частично инвариантны к ним. Аугментированная копия даёт вектор, близкий к исходному, и
   новой информации немного.
3. **Копии коррелированы с оригиналами.** Это не 9098 новых бабочек, а 9098 вариаций тех же 4549.

**Цена аугментации:** время обучения растёт пропорционально данным (×2,6–3,2), плюс однократно около
6 минут на признаки аугментированных изображений и 218 МБ на диске.

### 11.4. Выбор итоговой модели

По правилу «выбираем по val» лучший эксперимент — **logreg-aug** (val accuracy 0,9149). Его результат на
test — 0,9077, F1-macro 0,9090. Если спросят, почему не logreg-base, хотя у него test выше (0,9118): смотреть
на test при выборе нельзя, иначе это будет подгонка под тест. Разница между ними статистически
незначима. По сути обе модели одинаково хороши.

### 11.5. Как можно улучшить

- Дообучение (fine-tuning) EfficientNet на аугментированных данных — на GPU. Вот тогда аугментация
  раскроется.
- Онлайн-аугментация при дообучении.
- Подбор гиперпараметров: C для LR и SVM, γ для SVM. Его легко провести очередью экспериментов DVC:
  `dvc exp run --queue -S train.svm.C=1 ...` и `dvc exp run --run-all`.
- Более сильный извлекатель признаков (EfficientNet-B3, ConvNeXt, ViT).
- Кросс-валидация вместо одного разбиения: более надёжная оценка при маленьких выборках.
- Test-time augmentation: усреднение предсказаний по нескольким преобразованиям тестовой картинки.

## 12. Воспроизводимость

**Воспроизводимость** — возможность любому человеку получить тот же результат из репозитория.

| Источник случайности или различий | Как зафиксирован |
|---|---|
| Разбиение на выборки | `random_state = data.seed = 42` |
| Аугментация | `torch.manual_seed(augment.seed = 42)` |
| Модели (LR, SVM, RF) | `random_state = train.seed = 42` |
| Версии библиотек | `requirements.txt` с точными версиями |
| Данные | стадия `download` скачивает тот же датасет; хэши результата записаны в `dvc.lock` |
| Код и параметры каждого результата | git + `dvc.lock` + коммиты экспериментов |

**Ограничения, о которых стоит знать:**

- датасет на Kaggle может обновиться автором; изменение заметит `dvc status`, так как хэш `data/raw`
  разойдётся с `dvc.lock`;
- вычисления с плавающей точкой на разных процессорах и в разных версиях библиотек могут давать
  расхождения в последних знаках;
- remote DVC здесь — локальный каталог, поэтому на другой машине `dvc pull` не сработает. Данные там
  пересоздаются через `dvc repro`. Для командной работы нужен общий remote (S3, Google Drive, SSH).

## 14. Вопросы и ответы

### Про MLOps и инструменты

**Что такое MLOps и зачем он нужен?**
Практики автоматизации и версионирования полного цикла ML: данных, кода, параметров, моделей,
экспериментов. Нужен, чтобы результат можно было воспроизвести, объяснить («на чём и с какими параметрами
обучено») и надёжно обновлять.

**Какой уровень зрелости MLOps у работы?**
Уровень 1 по классификации Google: автоматизированный, воспроизводимый пайплайн с версионированием данных и
экспериментов. До уровня 2 не хватает CI/CD, развёртывания и мониторинга.

**Почему GitHub, а не GitLab?**
Задание разрешает другие инструменты. Для работы нужен только git-хостинг, а DVC работает с любым. GitLab
дал бы встроенный CI и Package Registry, но в этой работе они не используются.

**Что такое DVC и чем он отличается от Git?**
Git версионирует код, а DVC добавляет версионирование больших данных и моделей (хэши в git, файлы в кэше и
remote), пайплайны с кэшированием и эксперименты. DVC работает поверх git и использует его для хранения
метаданных.

**Почему не хранить данные прямо в git?**
Git хранит каждую версию каждого файла целиком и не рассчитан на большие бинарные файлы. Репозиторий бы
разросся, клонирование стало бы медленным, к тому же у GitHub есть ограничения на размер.

**Чем DVC отличается от MLflow?**
MLflow — трекер экспериментов с сервером и UI: метрики логируются из кода, есть реестр моделей и
развёртывание. DVC — версионирование данных и пайплайнов поверх git без сервера. Его эксперименты — это
git-коммиты, и метрики берутся из файлов. Инструменты часто используют вместе.

**Чем DVC отличается от Git LFS?**
LFS только хранит большие файлы вне git. В DVC вдобавок есть пайплайны, кэширование результатов стадий,
эксперименты, метрики и множество типов хранилищ.

### Про DVC подробно

**Где физически хранятся данные?**
В кэше DVC `.dvc/cache` (файлы названы по MD5-хэшу), в рабочей копии `data/` и копия в remote
`~/dvc-storage/...`. В git — только хэши в `dvc.lock`.

**Чем отличаются `dvc.yaml` и `dvc.lock`?**
`dvc.yaml` пишет человек: что запускать, от чего зависит, что производит. `dvc.lock` генерирует DVC: точные
хэши зависимостей и выходов и значения параметров последнего успешного запуска. Это «снимок» состояния
пайплайна.

**Как DVC понимает, что стадию надо перезапустить?**
Сравнивает текущие хэши `deps` и `outs` и значения `params` с `dvc.lock`. Если что-то отличается, стадия и
все зависящие от неё стадии перезапускаются.

**Что будет, если запустить `dvc repro` второй раз подряд?**
Ничего не выполнится: все стадии актуальны, DVC выведет, что стадии не изменились.

**Что перезапустится, если изменить `train.model`?**
Только `train` и `evaluate`: параметр `train` — зависимость стадии `train`, а `evaluate` зависит от её
выхода.

**Что перезапустится, если изменить `augment.rotation_deg`?**
`augment`, затем `featurize` (изменился вход `data/augmented`), затем `train` и `evaluate`. `download` и
`prepare` не перезапустятся.

**Что перезапустится, если изменить код `src/prepare.py`?**
`prepare` и всё после неё: `augment`, `featurize`, `train`, `evaluate`.

**Что такое run-cache?**
Кэш результатов всех прошлых запусков стадий. Если стадию запускают с теми же зависимостями и
параметрами, что когда-то раньше, DVC восстанавливает выходы из кэша без выполнения.

**Что значит `cache: false` у метрик?**
Файл не кладётся в кэш DVC, а хранится в git как обычный файл: он маленький и его удобно видеть в истории.

**Как устроен эксперимент DVC?**
Это скрытый git-коммит с изменёнными `params.yaml`, `dvc.lock` и метриками, записанный в ссылку
`refs/exps/<базовый коммит>/<имя>`. Данные эксперимента лежат в кэше DVC. Ссылка не видна в
`git log`/`git branch`, но отправляется на сервер (`dvc exp push`).

**Почему эксперименты не видны в `git log`?**
Они записаны не в ветки (`refs/heads`), а в отдельное пространство `refs/exps`, которое `git log` по
умолчанию не показывает. Это сделано, чтобы десятки экспериментов не засоряли историю.

**Чем `dvc exp apply` отличается от `git checkout`?**
`exp apply` переносит в рабочую копию изменения эксперимента (параметры, `dvc.lock`, метрики) и сразу
восстанавливает его данные и модель из кэша. Новый коммит не создаётся и ветка не меняется. Чтобы
закрепить результат, нужен обычный коммит.

**Как показать эксперимент коллеге?**
`dvc exp push origin <имя>` (или `--all`): коммит эксперимента уходит в git-remote, а его данные — в
DVC-remote. Коллега делает `dvc exp pull origin <имя>`, затем `dvc exp apply`. В нашей конфигурации remote
локальный, поэтому для коллеги пришлось бы настроить общий (S3, SSH, Google Drive).

**Как запустить много экспериментов сразу?**
`dvc exp run --queue -S ...` несколько раз, затем `dvc exp run --run-all -j 4`. Можно и сеткой:
`dvc exp run --queue -S 'train.svm.C=1,10,100'`.

**Как получить проект на новой машине?**
`git clone`, `pip install -r requirements.txt`, затем `dvc pull` (если remote доступен) или `dvc repro`
(данные скачаются с Kaggle и всё пересчитается), затем `dvc exp pull origin --all` для истории
экспериментов.

**Как добавить новую модель?**
Добавить ветку в `build_model()` в `src/train.py` и раздел с гиперпараметрами в `params.yaml`, затем
`dvc exp run -S train.model=<новая>`.

### Про данные

**Почему не использовали тестовую часть датасета с Kaggle?**
У неё нет меток (в `Testing_set.csv` только имена файлов), поэтому оценить на ней качество невозможно.
Тестовая выборка выделена из размеченных данных.

**Зачем нужна валидационная выборка, если есть тестовая?**
Чтобы выбирать модель, не глядя на test. Если выбирать по test, оценка станет оптимистичной: выбор
подогнан под конкретный тест.

**Что такое стратификация и зачем она?**
Разбиение с сохранением долей классов. Без неё при 75 классах и ~13 примерах класса в val/test какой-то
класс мог бы оказаться недопредставлен.

**Что такое утечка данных? Есть ли она у вас?**
Это попадание информации из тестовых данных в обучение. У нас её нет: аугментация делается после разбиения
и только для train, StandardScaler обучается только на train (внутри конвейера), признаки извлекаются
сетью, которая не обучалась на наших данных.

**Не является ли утечкой то, что EfficientNet обучалась на ImageNet, где есть бабочки?**
Нет. Утечка — это когда модель видела именно наши тестовые изображения. ImageNet — внешний датасет, и
использование знаний из него и есть суть переноса обучения.

**Почему 70/15/15?**
Стандартная пропорция: большая часть на обучение, а на val и test достаточно примеров (по 975, в среднем по
13 на класс) для оценки.

### Про модель и признаки

**Почему вы не обучали нейросеть?**
Нет GPU. Обучение или дообучение CNN на CPU заняло бы часы на каждый эксперимент. Перенос обучения с
извлечением признаков позволил посчитать признаки один раз за 10 минут и проводить эксперименты за
секунды. Задание при этом выполнено: пайплайн, 3 модели, аугментация, сравнение.

**Что такое перенос обучения?**
Использование модели, обученной на одной задаче (ImageNet), для другой (бабочки). У нас сеть используется
как замороженный извлекатель признаков, а обучается только классификатор поверх.

**Что такое вектор признаков из 1280 чисел?**
Выход сети после глобального усредняющего пулинга, без последнего классификационного слоя. Каждое число —
степень проявления на изображении некоторого визуального паттерна, выученного на ImageNet.

**Почему EfficientNet-B0?**
Хорошее соотношение качества и скорости: 77,7 % top-1 на ImageNet при 5,3 млн параметров. Быстро работает
на CPU. В `params.yaml` можно переключить на ResNet-50 или MobileNetV3.

**Зачем нормализация mean/std ImageNet?**
Сеть обучалась на изображениях с такой нормализацией. Если подать картинки в другом масштабе, распределение
входов не совпадёт с привычным для сети, и признаки испортятся.

**Зачем StandardScaler?**
Логистическая регрессия и SVM чувствительны к масштабу признаков: от него зависят регуляризация,
сходимость и расстояния в RBF-ядре. Скейлер приводит признаки к среднему 0 и дисперсии 1. Его параметры
считаются только по train.

**Объясните логистическую регрессию.**
Линейная модель: для каждого класса взвешенная сумма признаков, softmax превращает суммы в вероятности.
Обучается минимизацией кросс-энтропии с L2-регуляризацией, где C — обратная сила регуляризации. Решатель —
lbfgs.

**Объясните SVM.**
Ищет границу с максимальным зазором между классами, определяемую опорными векторами. RBF-ядро даёт
нелинейную границу. C — штраф за ошибки на обучении, γ — «радиус влияния» одной точки. Многоклассовость —
«один против одного»: 2775 бинарных классификаторов и голосование.

**Объясните случайный лес.**
500 деревьев решений. Каждое обучено на бутстреп-выборке и в каждом узле выбирает признак из случайных
√1280 ≈ 36. Ответ — голосование. Случайность делает деревья разнообразными, а усреднение снижает
переобучение.

**Почему лучшей оказалась простая логистическая регрессия?**
Признаки предобученной сети почти линейно разделимы (последний слой самой сети тоже линейный), а данных
мало для такой размерности: около 60 примеров на класс при 1280 признаках. Регуляризованная линейная модель
обобщает лучше гибких моделей, склонных к переобучению.

**Почему случайный лес худший?**
Деревья делят пространство по одному признаку за раз. В плотных 1280-мерных признаках CNN информация
распределена по многим признакам одновременно, и такие разбиения неэффективны.

### Про метрики

**Что такое accuracy, precision, recall, F1?**
Accuracy — доля верных ответов. Precision — доля верных среди предсказанных как класс k. Recall — доля
найденных среди всех настоящих k. F1 — их гармоническое среднее. Формулы — в разделе 9.

**Что значит macro?**
Метрика считается для каждого из 75 классов и просто усредняется: все классы весят одинаково.

**Почему кроме accuracy F1-macro?**
Классы немного несбалансированы (71–131). Accuracy может скрыть плохое распознавание редких классов,
F1-macro — нет.

**Как читать матрицу ошибок?**
Строка — истинный класс, столбец — предсказанный. Нормирована по строкам: на диагонали recall классов.
Внедиагональные точки — пары видов, которые модель путает.

### Про аугментацию

**Что такое аугментация и зачем она?**
Генерация новых обучающих примеров преобразованиями, не меняющими класс. Увеличивает разнообразие данных,
снижает переобучение.

**Почему аугментируется только обучающая выборка?**
Val и test должны отражать реальные данные и быть одинаковыми для всех экспериментов, иначе сравнение
нечестное. Аугментация тестовых данных до разбиения вызвала бы утечку.

**Какие преобразования и почему именно такие?**
Кадрирование с масштабом, горизонтальное отражение, поворот ±25°, изменение яркости, контраста и
насыщенности, размытие. Они имитируют реальные различия фотографий и не меняют вид бабочки. Сильный сдвиг
оттенка не используется, потому что цвет — ключевой признак вида.

**Почему по 2 копии на изображение?**
Компромисс: объём данных утраивается, при этом время извлечения признаков (~6 минут) и место на диске
(218 МБ) приемлемы. Это параметр `augment.copies_per_image`, его можно менять экспериментами.

**Офлайн или онлайн аугментация и почему?**
Офлайн: задание требует сохранить новый датасет, а при замороженной сети признаки считаются один раз, и
онлайн-аугментация потребовала бы пересчёта признаков на каждой эпохе.

**Как гарантируется, что аугментированный датасет воспроизводим?**
Фиксированный `torch.manual_seed(42)` и параметры в `params.yaml`. Хэш датасета записан в `dvc.lock`.

**Почему аугментация почти не помогла логистической регрессии?**
Сеть заморожена и уже частично инвариантна к этим преобразованиям (на ImageNet её обучали с похожими
аугментациями), поэтому признаки копий близки к признакам оригиналов. Линейная модель уже на пределе
качества признаков. Разница −0,41 п.п. на test — это 4 картинки, в пределах шума.

**Почему SVM выиграл от аугментации?**
SVM с RBF-ядром и C = 10 склонен переобучаться на маленькой выборке. Дополнительные точки вокруг каждого
примера делают области классов шире и плотнее, граница получается устойчивее: +1,95 п.п. на test и
+3,08 п.п. на val.

**Значимы ли различия?**
Одно тестовое изображение = 0,1 п.п. 95 %-й доверительный интервал accuracy ≈ ±1,8 п.п. Различия у LR и RF
незначимы, у SVM прирост заметный и согласованный на val и test.

**Почему выбрана logreg-aug, хотя у logreg-base test выше?**
Модель выбирается по val, на test смотреть при выборе нельзя. По val лучше logreg-aug (0,9149). Разница с
logreg-base в пределах шума, то есть модели практически равноценны.

### Про воспроизводимость и прочее

**Как обеспечена воспроизводимость?**
Seed везде, точные версии библиотек, загрузка данных как стадия пайплайна, хэши всех данных и результатов
в `dvc.lock`, параметры в `params.yaml`, эксперименты сохранены в git.

**Что если датасет на Kaggle изменится?**
`dvc status` покажет расхождение хэша `data/raw`. Из DVC-remote можно восстановить исходную версию
(`dvc pull`).

**Сколько занимает полный запуск?**
Загрузка около 1 минуты, аугментация около 1 минуты, признаки около 10 минут, обучение и оценка от
десятков секунд до минуты на модель.

**Что бы вы добавили для продакшена?**
CI (GitHub Actions: проверка кода и `dvc repro` на изменения), общий DVC-remote в облаке, реестр моделей,
сервис для предсказаний (FastAPI), мониторинг качества и дрейфа данных, автоматическое переобучение.

**Что такое дрейф данных?**
Изменение распределения входных данных в эксплуатации по сравнению с обучающими: другие камеры, сезоны,
новые виды. Качество модели падает, и её нужно переобучать. Мониторинг дрейфа — часть MLOps уровня 2.

## 15. Глоссарий

| Термин | Значение |
|---|---|
| MLOps | практики автоматизации и версионирования ML-систем |
| Пайплайн | последовательность шагов обработки данных и обучения, описанная кодом |
| Стадия (stage) | один шаг пайплайна DVC с командой, зависимостями и выходами |
| DAG | направленный ациклический граф зависимостей стадий |
| Кэш DVC | хранилище файлов, адресуемых по MD5-хэшу содержимого |
| Remote | удалённое хранилище (git-remote для кода, DVC-remote для данных) |
| Эксперимент DVC | сохранённый запуск пайплайна с параметрами и метриками (скрытый git-коммит) |
| Baseline | коммит, от которого запущены эксперименты |
| Гиперпараметр | параметр, задаваемый до обучения (C, γ, число деревьев) |
| Перенос обучения | использование модели, обученной на другой задаче |
| Извлечение признаков | использование замороженной сети для получения векторов признаков |
| Аугментация | генерация обучающих примеров преобразованиями, сохраняющими класс |
| Стратификация | разбиение с сохранением долей классов |
| Утечка данных | попадание информации из тестовых данных в обучение |
| Переобучение | модель запоминает обучающие данные и плохо работает на новых |
| Регуляризация | штраф за сложность модели, борется с переобучением |
| Softmax | функция, переводящая оценки классов в вероятности |
| Ядро RBF | функция сходства exp(−γ‖x−x'‖²), позволяющая SVM строить нелинейные границы |
| Bagging | обучение моделей ансамбля на бутстреп-выборках |
| Macro-усреднение | усреднение метрики по классам с равными весами |
| Матрица ошибок | таблица «истинный класс × предсказанный класс» |
| Seed | зерно генератора случайных чисел, фиксирует случайность |
